# Validation strategy

Use the acceptance cases in `ACCEPTANCE.json`; implement checks proportional to a small presentation site. Runtime tests belong to Codex's implementation, not this planning bundle. Never report a planned/manual check as executed.

## Local foundation

Record actual WordPress, PHP, browser and tool versions. Confirm theme activation on a disposable local site with core blocks only and no presentation plugin. PHP syntax checks and WordPress debug output must be clean. Test front-end and editor behavior with the same supported PHP major/minor family intended for IONOS. Use WP-CLI if available, not as an assumed hosting requirement.

## Content safety

Test seed plan mode, first apply, second apply with no changes, slug conflict with an unrelated page, and rerun after a user edits a field. Confirm no duplicate Pages, automatic publication or overwritten user content. Verify imports translate attachment IDs/URLs safely and leave unrelated options/users/pages untouched. Reinstall the theme and show the edit remains. These are meaningful tests of the principal data-loss risks.

## Browser checks

Exercise all seven pages plus home/support pages. At 320, 390, 768, 1024 and 1440 CSS-pixel widths verify no unintended horizontal overflow, legible headings and intact navigation/download controls. Capture representative screenshots at the specific handoff sizes. After final artwork, check every portrait/avatar at 390 and 1440 widths rather than assuming the pilot covers all silhouettes.

Use keyboard-only navigation, 200% zoom, JavaScript disabled and reduced motion. Navigation, copy and GitHub links must remain usable. Automated accessibility output is supplementary to actual focus/order/contrast inspection. Check Chrome/Edge and Firefox; add Safari coverage if available and state if not tested.

## Links and HTTP

Check internal links from the rendered site, actual status codes, canonical tags, duplicate titles/descriptions and social image URLs. Unknown routes must return HTTP 404, not a friendly 200. Avoid global redirect-to-home behavior. On launch verify apex HTTPS and www behavior without breaking existing unrelated paths/email DNS.

For GitHub releases use the exact repository/tag, confirm stable/public status, follow the actual advertised runtime ZIP, inspect the checksum sidecar and verify the downloaded bytes. Do not treat an HTTP 200 login/error page or a source-code archive as the intended runtime ZIP. Record timestamps and final URLs; timeouts/rate limits mean unverified, not failed software. Do not run the PowerShell applications as part of this website-only scope unless separately requested.

## Artwork and performance

Record slot-to-file mapping and supplied approvals. Check dimensions, alpha on dark/light backgrounds, artifact-free edges, actual crops and any social title text. Verify browser-selected `srcset` sizes, intrinsic dimensions, eager hero vs lazy lower-page media and no duplicate desktop/mobile downloads.

Provisional goals after final art: mobile first-view transfer around 1.5 MiB or less, theme-specific compressed CSS under 50 KB, optional theme JS under 15 KB, and CLS under 0.1 in a repeatable lab run. Aim for LCP ≤2.5 s on a documented mobile test, but report actual device/network/hosting variability. These are review targets, not a reason to heavily damage approved art or pretend a lab score proves field performance. Document material misses and reduce avoidable cost.

Inspect a signed-out browser's network panel for third-party requests, external fonts, trackers and mixed content. Review hosting-injected behavior separately from theme code. Do not claim zero cookies/tracking from source inspection alone.

## Deployment rehearsal

Install the exact produced theme ZIP on a disposable/private WordPress instance and recreate content/media through the documented route. Check package contents for secrets, debug data, handoff files and unapproved masters. Back up theme, DB/content and uploads; restore to a disposable environment and verify a page and representative image. After launch editorial work begins, production DB/uploads remain authoritative.

## Evidence format

Each result includes case ID, actual time, commit/package hash, environment, steps/command, expected vs observed, screenshot/log path, pass/fail/blocked and limits. Redact accounts, filesystem secrets and credentials. Keep an index; no fabricated screenshots, fake Lighthouse results or auto-passing placeholders. Record exactly which checks must be rerun when code/content/assets change.

## GitHub/source provenance checks

Verify all 47 asset sources and 33 selected slots against the allowlist and actual hashes; reject tool-repository imagery. Validate the final public repository visibility, code license, tag/commit, clean-clone build and public derivative coverage. Test ordinary repository-cleanup diffs/link/package impact and record actual default-branch results for all seven tools. These are actual implementation checks, separate from the shipped offline handoff tests.
